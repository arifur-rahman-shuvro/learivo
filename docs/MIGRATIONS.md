# Database migrations and how to undo each one

Files are in `supabase/migrations/`, applied in date order. Every migration so far is **additive** (new tables, new nullable or defaulted columns, new functions, new indexes), so the live app and an older app version keep working while a migration is applied.

**Before undoing anything:** download a backup (Account > Data > Backup) and note that dropping a column or table deletes its data for good. Run the SQL in Supabase > SQL Editor. Undo newest first. If a migration only added something the app no longer reads, the safest "undo" is to leave it in place.

## Rules for new migrations

1. Additive first: add the column or table, ship the app that uses it, and remove old things in a later migration.
2. Apply the migration **before** deploying the app code that reads it (the app selects the new column by name).
3. Put the rollback SQL in a comment at the top of the file, add the file to the list in `.github/workflows/ci.yml`, and add a check in `supabase/tests/` that fails when it is wrong.
4. Run it in a plain Postgres first (CI does this), then apply it to the live project with the exact SQL shown to the owner.
